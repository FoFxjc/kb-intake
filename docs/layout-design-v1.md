> 依据：[内容类型设计](content-types.md)（§3 内容路由）、[OCR 设计](ocr-design.md)、[OCR O-1 报告](ocr-o1-report.md)、[表格底座报告](tables-base-report.md)、[Docling 评估](docling-eval-v1.md)
> 一句话：不管是原生 PDF 还是扫描件，每一页都先切成**区域**，并给每个区域判一个**内容类型**（正文、标题、表格、图表、照片、印章……）。区域是入库的基本单位：后面的 OCR、表格底座、各内容处理器都按区域工作；文档页上把每个区域的框和类型画出来。
> 本文取代 OCR 设计 §7 的 O-2 至 O-4：OCR 不再是独立的一条线，而是区域流水线里的一步（只给没有原生文字的区域做）。

## 0. 为什么要换思路

现在的做法都建立在**原生文字层**上：建树、找表格、分词、概念打标都读文字层，图片区域靠“有没有原生文字”来判断。这有三个问题：

| 问题 | 例子 |
|---|---|
| 扫描件什么都没有 | 没有文字层，建树、找表格、按文字判断类型全部失效；OCR 补回文字后，仍然不知道哪块是表格、哪块是图表 |
| 每种内容各写一套规则 | 表格靠 `find_tables`，图表靠绘图簇，照片靠颜色，脚注靠字号；规则互不相通，探针和底座报告里的误判大多出在这里 |
| 类型判断依赖文字层的质量 | 表头丢失、合并格、信息图被认成表格，都是因为从文字层倒推版面 |

新思路是把“这一块是什么”当成一个**分类问题**，在**页面图像**上解决：同一个版面模型，对原生页和扫描页给出同样的区域与类型；原生文字层只用来**补充和校验**，不再是唯一依据。

## 1. 目标

1. 任意 PDF（原生、扫描、混合）的每一页，都得到一组区域：位置、类型、子类型、置信度、文字来源。
2. 同一页的原生版和扫描版，区域与类型一致（可以直接测，见 §6）。
3. 区域是内容路由的单位：每个区域都有归属的处理器，或者明确标为“丢弃”“未处理”。
4. 文档页能显示识别框：按类型着色，可筛选，可点开看详情。
5. 守住原则：入库不调用生成式大模型；模型版本固定；同一原件重建结果相同。

## 2. 区域类型

统一的类型表（版面模型的类别映射到这里，不同模型的类别名不直接外露）：

| 大类 | 类型 `type` | 子类型 `subtype`（第二阶段） | 交给谁（内容类型设计） |
|---|---|---|---|
| 文字 | `title` 文档标题 / `heading` 章节标题 | — | 4.1 目录与标题（建树的依据之一） |
| | `text` 正文段落 / `list` 列表 | — | 4.3 正文、4.4 正文数字、4.5 定义、4.6 前瞻 |
| | `caption` 图表标题 | `table_caption` / `figure_caption` | 挂到相邻的表格或图表上 |
| | `footnote` 脚注 | — | 4.11 修饰信息 |
| | `page_header` / `page_footer` / `page_number` | — | 不入正文；页码用于印刷页码校验 |
| | `toc` 目录 | — | 建树 |
| 表格 | `table` | 由表格底座与处理器细分：指标 / 分解 / 变动 / 名单 / 文字表格 | 表格共同底座 → 4.7–4.10 |
| 图形 | `chart` 图表 | `bar` / `line` / `pie` / `flow` / `map` / `other` | 4.12 图表（标题与图中文字入库，数值不解读） |
| | `diagram` 示意图、信息图 | — | 4.12 |
| | `picture` 照片 | — | 丢弃（4.14） |
| | `logo` / `icon` | — | 丢弃 |
| | `signature` / `stamp` 签名、印章 | — | 只记存在与位置（审计、扫描件真伪用），内容不入库 |
| | `screenshot` 截图 | — | 按图中文字处理，同 `diagram` |
| 其他 | `formula` | — | 原样保留，按正文检索 |
| | `unknown` | — | 进内容盘点的“未处理” |

## 3. 流水线

```text
原件 PDF
  │
  ├─① 页面渲染（固定 DPI）──────────────► 页面图像
  │
  ├─② 版面检测（模型，作用在页面图像上）──► 候选区域 [bbox, 类型, 置信度]
  │
  ├─③ 原生证据（PyMuPDF）：文字层、矢量绘图、内嵌图片、find_tables
  │
  ├─④ 融合：模型候选 × 原生证据 ─────────► 区域（类型定稿、去重、阅读顺序）
  │
  ├─⑤ 图形子分类（模型，只对 chart / diagram / picture 候选）──► 子类型；照片、图标判为丢弃
  │
  ├─⑥ 区域文字：有原生文字 → 用原生；没有 → OCR（只对要保留的区域）
  │
  └─⑦ 路由：区域 → 内容处理器（表格底座、正文、图表……）；写入 region 记录与内容盘点
```

### 3.1 ② 版面检测

- 输入页面图像，输出候选区域。原生页和扫描页走同一个模型。
- 候选模型（开工前实测，许可证逐个核实）：

| 候选 | 类别 | 备注 |
|---|---|---|
| PaddleOCR 的 PP-DocLayout 系列 | plus-L 为 20 类，含 `chart`、`seal`、页眉页脚、脚注、公式 | 中文文档训练充分；与 O-1 用过的 RapidOCR 同源 |
| Docling 的版面模型（Heron，RT-DETRv2） | 17 类（DocLayNet 体系），图形只有 `Picture` 一类 | 图形细分要配 ⑤ 的图形分类器 |
| 其他 | DocLayout-YOLO 等 | 先查许可证（YOLO 系常见 AGPL，企业环境可能不能用） |

- 只用小型检测模型（几千万参数），CPU 可跑；不是生成式模型。

#### 现成的开源方案（2026-10 调研，许可证以原文和法务意见为准）

②③⑤⑥ 有成套的开源实现，优先**整套接入**，而不是自己拼模型。它们只作为“版面引擎”放在区域接口后面；融合规则、区域类型表、路由和 UI 仍是我们自己的。

| 方案 | 做什么 | 许可（代码 / 权重） | 与本项目的契合度 |
|---|---|---|---|
| **Docling**（IBM，LF AI） | 版面检测（DocLayNet 类别）+ 表格结构（TableFormer）+ 图形分类 + 可插拔 OCR（含 RapidOCR、Tesseract）；输出带每个元素出处与坐标的结构化文档 | MIT / 默认权重为宽松许可（Apache、CDLA、MIT） | **首选**：许可最干净，CPU 可跑，结构化输出带坐标，小模型流水线。OCBC 2025 实测见 docling-eval-v1 |
| **PaddleOCR PP-StructureV3** | 版面检测（含图表、印章、页眉页脚）+ OCR + 表格识别 + 印章识别 + 公式 + 图表解析（可选） | Apache-2.0（核实） | **次选**：中文最强，类别更全；依赖 Paddle 框架，部署较重 |
| MinerU | 流水线后端（小模型）与 VLM 后端；中间 JSON 带坐标 | 改为基于 Apache 的自有许可，有商用门槛与署名要求；部分权重未标许可 | 需法务看条款；实际要 GPU |
| Marker / Surya | 版面、OCR、表格 | 代码 Apache；Surya 权重为修改版 OpenRAIL-M，有营收、融资与竞争条款 | 企业环境风险高，不选 |
| Unstructured | 分区（partition），hi_res 模式用版面模型 | Apache-2.0 | 偏 RAG 切块，区域类型较粗 |
| 视觉语言模型方案（granite-docling、PaddleOCR-VL、dots.ocr、olmOCR 等） | 整页读成结构化文本 | 各异 | 属于生成式模型，与“入库不调用生成式模型、结果可复现”冲突；只作为难页的后备或查询时使用 |

L-1 的选型就在 Docling 与 PP-StructureV3 之间实测，标准答案与 §6 相同。demo 阶段先用 Docling（待确认），PP-StructureV3 对比推迟。

### 3.2 ③④ 融合：模型与原生证据互相校验

模型看图像，原生证据看 PDF 内部结构，两者各有长短。融合规则（第一版，实测后调；表格相关规则以 intake-design-v1 §9.2 为准）：

| 情况 | 处理 |
|---|---|
| 模型判 `table`，`find_tables` 也找到重叠的表 | 采用；行列结构用 Docling（TableFormer），`find_tables` 做数字比对，不一致记 `table_cross_mismatch`（2026-10-20 修订：原为“行列结构用 find_tables”，Docling 实测数字错位为 0，find_tables 未实测） |
| 模型判 `table`，`find_tables` 没找到 | 采用模型的框和 TableFormer 结构；文字守恒检查不过的进 gaps。扫描页上行列结构留给表格底座（用 OCR 词坐标重建） |
| `find_tables` 找到，模型判成 `chart` / `diagram` / `picture` | 按模型；`find_tables` 的结果标为误识别 |
| `find_tables` 找到，模型判成 `text` 或没有区域，且通过文字守恒检查 | 采用 `find_tables` 的表，记 `table_missed`（2026-10-20 修订：原规则会丢掉 OCBC p106 这类被模型拆成正文的真表） |
| 模型判 `picture`，区域内原生文字很多 | 改判 `diagram`（信息图：图上压着原生文字） |
| 模型判 `text`，区域被矢量绘图簇覆盖且多为数字 | 改判 `chart`，并标低置信度 |
| 原生文字块不在任何区域里 | 补一个 `text` 区域，标 `source = native_only`，进抽检 |

每个区域记下类型的**来源**（`model` / `native` / `fused`）和两边是否一致，方便查错。

### 3.3 ⑤ 图形子分类

对 `chart` / `diagram` / `picture` 候选，用一个小型图像分类器判子类型。候选：Docling 的 DocumentFigureClassifier（16 类：柱状图、折线图、饼图、流程图、地图、截图、标志、图标、签名、印章、条码、二维码等，MIT 许可，约 400 万参数）。

- 照片、图标、标志：丢弃，不做 OCR（取代 O-1 的“送 OCR、识别不出文字才丢”）。
- 图表：保留；标题与图中文字入库（原生或 OCR），**数值不在入库时解读**。查询时需要数值，由 agent 看原图。
- 签名、印章：只记存在与位置。

### 3.4 ⑥ 区域文字与 OCR

- 区域里原生文字够多 → 用原生文字（`text_source = native`）。
- 否则，且区域要保留 → OCR（`text_source = ocr`，带置信度）。OCR 引擎按 OCR 设计 §3 实测选定。
- 扫描页上的表格：OCR 出词坐标，表格底座在词坐标上重建行列（同一套表头还原、行路径逻辑）。

### 3.5 确定性

- 模型权重、推理库版本、渲染 DPI 固定，记在每个区域上（`layout_model`、`layout_version`）。
- 结果作为中间产物缓存：键为“原件 sha256 + 模型版本 + 参数”。重建时命中缓存就直接复用，所以同一份原件入库结果逐字节相同。
- 只用 CPU 推理，避免 GPU 的数值差异。

## 4. 数据模型

新增 L3 `region`（Doris 与 JSONL，和 `page`、`table_block` 并列；在 kb-intake 里生成，入件包中为 `regions.jsonl`）：

| 字段 | 说明 |
|---|---|
| `region_id` | `{doc_id}:p{page}:r{nn}`，按阅读顺序编号 |
| `doc_id`、`page_no`、`bbox` | 位置（PDF 点，左上为原点，与词坐标一致） |
| `type`、`subtype` | §2 的类型 |
| `score` | 类型置信度 |
| `type_source` | `model` / `native` / `fused`；`agree`：模型与原生证据是否一致 |
| `text_source`、`ocr_confidence`、`text` | 区域文字及其来源 |
| `status` | `kept` / `discarded` / `unhandled` |
| `handler`、`ref` | 交给了哪个处理器，以及对应记录（如 `table_id`） |
| `reading_order` | 阅读顺序 |
| `layout_model`、`layout_version` | 模型与版本 |

关系：
- `table_block` 增加 `region_id`；扫描页上的表格也从区域出发。
- `page` 增加 `kind`（原生 / 扫描 / 混合 / 空白，来自 O-1）与区域类型的计数。
- 内容盘点（内容类型设计 §6）直接由 `region` 汇总得出。

## 5. UI：文档页的识别框

| 位置 | 做法 |
|---|---|
| V3 文档与证据 | 页面上叠加区域框，按类型着色（文字类灰蓝、表格蓝、图表品红、印章红、丢弃的照片和图标浅灰虚线）。图例可逐类开关。默认显示表格、图表、印章、未处理；正文默认隐藏，避免满屏框 |
| 区域详情 | 点一个框：类型、子类型、置信度、类型来源（模型 / 原生 / 融合，是否一致）、文字来源与 OCR 置信度、交给的处理器和对应记录（表格可跳到表格结构） |
| 低置信度 | 置信度低于阈值、或模型与原生证据不一致的框，用虚线加问号标出，并能“只看可疑区域” |
| 页面标签 | 页头显示页类别（原生 / 扫描 / 混合）和本页各类区域数 |
| V5 入库看板 | 每份文档一条区域构成条（文字 / 表格 / 图表 / 丢弃 / 未处理），点开到 V3 对应页 |

叠加层数据走现有的叠加接口（`/v1/admin/docs/{doc_id}/pages/{page_no}/overlays`），增加 `regions` 一项。

## 6. 怎么验证

| 测什么 | 怎么测 |
|---|---|
| 区域类型准确率 | 人工标一批页面的区域（框 + 类型）作为标准答案：6 份年报约 60 页，按章节分层抽（含财务重点、报表、附注、治理、照片页、信息图页），另加其他类型文档若干页。按类型算精确率和召回率（框重叠 ≥ 0.5 算匹配） |
| 原生与扫描一致 | O-1 的合成扫描集是同一批页面的纯图片版：扫描版的区域与类型应当与原生版一致。这是不用人工标注就能做的回归测试 |
| 融合的价值 | 分别统计“只用模型”“只用原生规则”“融合”三种结果在标准答案上的得分 |
| 对下游的影响 | 6 份年报重建后，表格底座的抽检项不变坏；召回评测逐题不变（区域只增加字段，第一阶段不改检索） |
| 速度与确定性 | 每页耗时、内存；同一原件两次入库逐字节相同 |

## 7. 顺序

| 步 | 内容 | 结束标志 |
|---|---|---|
| L-1 | 标注区域标准答案；版面模型与图形分类器实测选型（2–3 个候选，含原生与扫描两版） | 选型报告（各类型精确率 / 召回率、原生与扫描一致率、耗时、许可证），等确认 |
| L-2 | 入库加区域阶段：渲染、检测、融合、子分类、写 `region`；O-1 的页分类改为由区域汇总 | 标准答案上达到 L-1 定的线；6 份年报下游不变 |
| L-3 | UI：V3 识别框与区域详情、V5 区域构成 | 截图与演示路径 |
| L-4 | 区域文字：OCR 接入（只给需要的区域）；扫描页上的表格在 OCR 词坐标上走表格底座 | 合成扫描集全流程走通，3 道演示题在扫描版上能答 |

每步一个 PR，结束写报告，停下等确认。L-2 在 kb-intake 里实现，与 intake-design 迁移计划的 3b 合并进行。

| 已有 | 变化 |
|---|---|
| O-1 按页分类（`pipeline/pages.py`） | 保留作为不依赖模型的快速判断；L-2 之后页类别由区域汇总，两者不一致时进抽检 |

## 9. 不做的

- 用生成式视觉大模型在入库时理解图表、读出数值。
- 手写体识别。
- 训练或微调版面模型（先用现成模型；标准答案里如果某类持续不达标，再另行立项）。
